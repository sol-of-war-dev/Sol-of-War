# Sol of War payment architecture

Start with [How funds and payouts work](PAYOUTS.md) for the player-facing guide. This document describes the implementation reviewed October 29, 2026. The default local mode is simulation; the code also supports invite-only devnet and explicitly configured mainnet. Source code and historical signing checks do not establish the live network, balances, provider policies or a successful funded rehearsal. See [DEVNET.md](DEVNET.md), [MAINNET.md](MAINNET.md) and [VERIFICATION.md](VERIFICATION.md).

## Custody and network boundaries

The application controls account-wallet signing keys; per-match pools use platform-authorized signing through Privy. These are custodial wallets, not a smart-contract escrow that independently decides game results. Control of the runtime/keyring or pool-signing authority can mean control of funds. Application safeguards and constrained admin endpoints do not eliminate that trust.

The transport checks the configured network's genesis hash, and the database is bound to one network. Mainnet requires separate configured custody credentials and a separate fee payer from devnet. The treasury and network fee payer must also be different wallets. No real transactions are sent in simulation; devnet uses test SOL.

## Economics

- Treasury: captured from server configuration in each match funding record. Mainnet requires an explicit treasury address. Historical test/configuration addresses are not personal deposit instructions or proof of current production settings.
- 1% of the gross locked pool goes to the treasury. FFA/1v1 pay the other 99% to the winner; 2v2 splits it between the two registered winning teammates.
- Full entry refunds on cancellation or a verified winnerless game; no platform fee. An original external-sender deposit network fee is not refundable.
- The platform uses a separate fee payer for payouts and refunds, preserving the advertised prize and full refund.
- Integer lamports throughout; any odd team remainder follows frozen roster order.
- Business entry/pool caps are optional configuration; precision and full-pool overflow checks always apply. The source alone does not establish production caps.

The lobby displays the gross pool before the fee. A potential pool assumes all slots are funded; settlement uses the locked funded roster. The fee is `floor(gross lamports * 100 / 10000)`. Prize rounding cannot add to the fee. Payouts include each winner's own entry and are not net profit. Both registered winning teammates receive their share even if one disconnected after lock.

| Example | Gross | Treasury | Each winner |
| --- | ---: | ---: | ---: |
| 1v1, 0.25 SOL each | 0.5 | 0.005 | 0.495 |
| 2v2, 0.25 SOL each | 1 | 0.01 | 0.495 |
| 25-player FFA, 0.25 SOL each | 6.25 | 0.0625 | 6.1875 |

## Account-wallet funding and withdrawals

When account wallets are enabled, an external wallet signs a top-up into the player's dedicated account wallet. Top-up fees are paid by that external wallet. Account keys are generated by the application and encrypted at rest; they do not use Privy wallet provisioning. See [PLAYER_WALLETS.md](PLAYER_WALLETS.md).

Confirming a paid entry in the app authorizes the server to reserve and transfer that amount from the account wallet to the match pool. This does not require another external-wallet signature. The authenticated identity, not a client-supplied owner ID, selects the account. Repeated requests reuse the original transfer ID and terms. Reservations prevent concurrent overspending, and balance reads require finalized commitment at a slot covering completed outgoing transfers. Unique memos distinguish otherwise identical transfers.

The confirmed account funding address becomes the locked payout/refund destination. Winnings return there before a separate withdrawal. Existing externally funded entries retain their original destinations. Account-wallet entries and withdrawals use the platform's fee payer; no extra withdrawal commission is implemented.

Withdrawals permit a user-confirmed valid Solana destination, defaulting to the linked external wallet. They are not restricted to that linked address. The minimum is 0.001 SOL or the full available balance, with rent-remainder checks and route rate limits. The signed-in session authorizes spending; address format validation does not prove recipient ownership. A retry cannot change the original account, amount or destination. Pending/uncertain transfers retain their reservation across restarts. A definitive pre-broadcast failure or finalized on-chain failure releases its account reservation.

## Direct external-wallet entry flow

This route applies when account funding is disabled or an existing entry retains its external-wallet funding path. The result and settlement checks below also apply to account-funded matches.

1. Privy verifies the selected external wallet; the player must claim a username. A server-side tester allowlist restricts devnet admission; mainnet requires an explicit invite/public setting. The tutorial remains free and anonymous.
2. Players may enter an open or queued lobby. A wallet is provisioned lazily for that match, using a persisted unique external ID, explicit owner and policies. A lost creation response is reconciled by external ID; never substitute another pool.
3. Each player requests a server-built direct SOL transfer for their exact stake and pool. The frontend asks the authenticated wallet to sign on the selected network. Sign-in is not a payment approval.
4. The backend verifies the Ed25519 signature, the exact native-SOL amount and pool destination, and the authenticated player as sole signer/fee payer. External wallets may recompile legacy/v0 messages, add compute-unit limit/price instructions, or refresh a valid network blockhash; other instructions, recipients, signers and lookup tables are rejected. The accepted signed bytes are persisted before broadcast and reused on retries. Each authenticated player/wallet gets one deposit intent per match. Platform payout/refund signatures still require byte-identical messages.
5. The worker credits only a finalized successful signature on the genesis-verified network. Only funded, connected human players contribute to the eligible pool. At match start, lock the funded roster, entry amounts and payout addresses synchronously. Unfunded seats cannot start. Underfilled lobbies close at their deadline and funded entries are queued for refunds; later queued lobbies advance under the lobby rules.
6. Signed deposits that finalize after exclusion, cancellation or departure remain tracked and get full refunds. Leaving after start does not alter the locked entitlement. Waiting and interrupted playing matches are cancelled on restart; signed jobs and refund records survive in SQLite.
7. Independently replay the archived game on the server. Client win votes never authorize payment. Unverifiable outcomes stay in review. Valid results create an immutable settlement plan from the funded roster.
8. Sign treasury fee and every winner transfer in **one atomic transaction**, using the separate platform fee payer. Persist all signed bytes before broadcasting. Reconcile or rebroadcast those same bytes on ordinary retries; a timeout does not justify a replacement payout. The reviewed finalized-failure recovery below is separate. Entries and individual refunds are not part of this atomic settlement transaction.
9. Mark the result paid only after finalization. Deposit/refund receipts remain available after the lobby disappears, and payout receipts appear in match history. Admin financial totals identify the network and count finalized payouts/fees/refunds.

## Implementation

- `DevnetPayments.ts`: per-seat funding, managed pool provisioning, funded roster gate, cancellation/refund worker and verified settlement adapter.
- `DevnetTransactions.ts`: Solana Kit transaction construction, strict platform signature/message verification, genesis guard, durable signed transaction transport and reconciliation.
- `DepositSignature.ts`: constrained external-wallet payment validation, optional network-fee instructions, and blockhash/finalized-history checks.
- `PrivyTransactionSigner.ts`: canonical JSON / P-256 authorization for the managed pool and fee-payer signer. Server credentials authorize signing; no pool Solana private key is exported through this integration. Account keys use the separate application vault described above.
- `PaymentRoutes.ts`: authenticated deposit/receipt routes. Session identity supplies the player and wallet, not client body fields.
- `PaymentConfig.ts`, `Network.ts`, `PaymentDatabase.ts`: explicit chain/configuration, separate production custody and immutable database network binding. Simulation remains the default.
- `DevnetPayments.ts` and `DevnetTransactions.ts` now serve both funded networks; historical filenames are retained for compatibility.
- `PoolReconciliation.ts`: finalized history, exact entry recovery and balance discrepancy reporting.
- `Backups.ts`, `PaymentMonitoring.ts`: encrypted backup/restore and fee-payer/backup/reconciliation alerts.
- `SettlementOutbox.ts`: immutable plan, exact 1% conservation, durable claim and confirmation tracking.
- `Operations.ts` and `OperationsView.ts`: persistent admission pause, protected payment review queue, original-signature checks, worker health and administrator audit history. See [OPERATIONS.md](OPERATIONS.md).
- `PrivyLogin.ts`, `PaymentView.ts`, `App.ts`: wallet approval, payment states, transaction links and devnet labels. Win-card amounts remain estimates until independent verification and payout confirmation.
- `FundingBook.ts` and `DepositVerifier.ts`: earlier fixed-roster/import-verification adapters retained for isolated testing. The live integration uses per-seat immutable wire transactions instead, allowing people to enter the global queue dynamically.

## Verification and known limits

See [DEVNET.md](DEVNET.md) for setup. The committed code is not evidence of an on-chain rehearsal. The existing automated tests use local RPC/provider fixtures and actual transaction signatures, with no network funds. A separate real-wallet run must exercise Privy policies, transaction approval, deposits, payout, cancellation and restart recovery.

Failed or expired signed transactions are held for review. An audited admin status check can recover an original signature that later finalizes. A supported outgoing payout/refund/return retry requires a finalized on-chain failure and may change only the blockhash; it preserves source, fee payer, recipients and amounts and archives every signed attempt before broadcast. Absent or expired signatures cannot be replaced blindly. No fixed payment-completion deadline is guaranteed.

The scanner can recover an exact issued entry submitted outside the normal endpoint. Other manual, unsolicited and excess transfers are listed separately, never credited as a seat/prize. The implemented `UnmatchedReturns` flow can return an eligible direct native-SOL transfer to its proven original sender, for the original amount, after checking that recorded obligations remain covered. Ambiguous/program-mediated transfers are not automatically returnable. See [OPERATIONS.md](OPERATIONS.md#returning-an-accidental-deposit).

Manual result review checks each participant against the original funding address locked into the match: the account wallet for balance-funded entries, or the original external wallet for legacy entries. It requires finalized deposits, matching amounts and an uncancelled locked roster, and refuses entries with an existing refund or matches with a verified result or settlement plan. Administrators can replay the saved recording or refund the original entries; they cannot substitute recipients or winners. [Account-wallet regression tests](tests/frontpot/PlayerWallets.test.ts) exercise replay, full refunds, mixed funding, 1v1/2v2, restart recovery and rejection of altered destinations, unfinalized deposits, cancelled entries and duplicate refunds on both network configurations, using mocked RPC.

Only one application process owns the SQLite volume and in-memory games. Use deployment preparation to close waiting lobbies, refund entries and let active games finish before a planned restart. Forced deployments/crashes can interrupt games; durable records drive refunds and saved-result recovery rather than resuming live gameplay. Encrypted backup restoration remains held until chain reconciliation. Account signing runs in the application process; runtime/keyring compromise or loss of recovery keys can compromise or strand funds.

This repository does not include an independent custody/security audit or a complete public mainnet receipt set covering top-up, entry, payout, refund and withdrawal on a named deployed release. Live provider policies, restore drills, fee-payer balances, external alert delivery and support response times need separate dated evidence. On-chain receipts establish transfers, not overall solvency or independent game fairness. A verification hash binds the stored recording/result; it is not an on-chain fairness proof.

An incoming receipt has one durable purpose: funding an entry or returning an accidental deposit. Entry recording and return-plan creation check and claim the signature inside SQLite write transactions. A return plan reserves its receipt before signing, and the reservation survives signing failures and restarts. Startup stops for reconciliation if a restored database contains both claims. Wallet-adjusted issued entries are recovered through the entry path; additional same-amount transfers remain visible as unmatched deposits. [Receipt regression tests](tests/frontpot/DevnetFlow.test.ts) cover returned-receipt reuse, both orderings of overlapping requests, pre-broadcast signing failure, restart recovery, conflicting restored state and duplicate transfers.
